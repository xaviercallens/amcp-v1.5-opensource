AMCP v2.4 – Current State and Roadmap (v1.5 – v2.4)
Overview: The Agent Mesh Communication Protocol (AMCP) has reached version v1.4, delivering a solid foundation for multi-agent systems with features like asynchronous pub/sub messaging, agent mobility (Aglet-style), tool integration (MCP/A2A), and multi-broker support  . In this report, we first analyze AMCP v1.4 as implemented (per the GitHub repository and formal spec) and how it aligns with the initial technical specification and marketing goals. We then present a ten-step version roadmap from v1.5 through v2.4, outlining the evolution of AMCP’s capabilities. Each version section details the key protocol enhancements, interface updates, security improvements, integration features, deployment/observability upgrades, test coverage, and example use cases that demonstrate the new capabilities. This roadmap is designed to fulfill the strategic objectives from the marketing plan – namely fostering open-source adoption, enabling a SaaS platform, supporting hybrid enterprise deployments, and differentiating AMCP against competing frameworks – culminating in a robust open-source standard for agent communication.


AMCP v1.4 – Analysis of the Current State
Protocol & Architecture: AMCP v1.4 implements the core design laid out in the v1.0 specification , with several critical enhancements introduced over the v1.x series to date:
Event-Driven Publish/Subscribe Core: Agents in v1.4 communicate through an asynchronous event mesh rather than direct calls. This decoupled design (highlighted as a key principle in the spec ) is fully realized – an agent can publish an event on a topic, and any number of other agents subscribe to that topic will receive it, enabling many-to-many interactions. This is a departure from earlier point-to-point RPC approaches (like Google’s A2A). In fact, v1.4’s messaging layer supports modeling A2A-style request/response as a special case of events (one agent publishes a request event and expects a corresponding response event), thus generalizing and extending A2A’s capabilities . By using a pub/sub model, AMCP v1.4 allows multiple agents to react to the same event and enables non-blocking workflows, addressing the limitations of pure RPC protocols .
Agent Mobility (IBM Aglet-style Strong Mobility): A hallmark of v1.4 is built-in support for agent migration and cloning, aligning with IBM Aglets’ notion of strong mobility where an agent’s code and state can move between contexts at runtime. The spec formalizes this with operations like dispatchAgent, cloneAgent, and retractAgent. In v1.4, each agent implements onSaveState() and onLoadState() hooks so that its complete state can be serialized before migration and restored after. The AgentContext and MigrationManager coordinate to ensure the agent is quiesced, state safely transferred, and no duplicate instances exist during hand-off (meeting the safety invariant that an AgentID is active in at most one context at a time ). This means v1.4 agents can literally travel across the network – e.g. a “TrafficOptimizer” agent detecting a jam in the cloud can dispatch itself to an edge context by the intersection, act there, then return – all state intact. Such strong mobility was prototyped in v1.3 and is fully supported in v1.4 (including state serialization of active tasks, subscription migration, etc.). The formal spec’s proof sketches on migration safety (ensuring no message loss or duplicate processing) apply to v1.4’s implementation , which has been validated with unit tests that simulate agent moves and verify state consistency and event delivery order.
Lifecycle Management & Callbacks: Along with mobility, v1.4 enforces a strict agent lifecycle state machine. Agents transition through INACTIVE -> ACTIVE -> (MIGRATING) -> … -> TERMINATED with well-defined callbacks. The code ensures onCreate/onStart (called upon activation), onDeactivate (before migration or shutdown), and onDestroy (on termination) are always invoked in order. This addresses earlier gaps (noted around v1.1) where these methods weren’t guaranteed to run in all scenarios. V1.4’s AgentContext enforces these calls, improving reliability. For example, the system now guarantees an agent’s onDeactivate() will run and complete (or time out) before its state is saved and moved – ensuring resources are closed properly. This strict lifecycle adherence was a key compliance fix (one of the “top 5 enhancements” earlier in the roadmap ) and brings AMCP v1.4 in line with its formal specification and the AMCP mobility model.
Tool Integration (MCP and Beyond): V1.4 expands agents’ ability to call external tools and services securely. Earlier versions introduced a callMCPTool() API, but lacked a way to propagate credentials/tokens. V1.4 addresses this by adding an AuthenticationContext that carries OAuth tokens or API keys through agent tool calls. Now an agent invoking, say, a DuckDuckGo search MCP server or a Weather API can include its auth token, which the ToolConnector will validate and pass along (ensuring compliance with the tool’s auth requirements). This was a known issue resolved from v1.2. Also, v1.4’s ToolConnector interface is developer-friendly: it provides an AbstractToolConnector with default no-op methods for optional features, so developers implementing a new tool only override what’s necessary (this improvement reduces boilerplate, reflecting the “ToolConnector developer experience” goal ). Combined, these changes mean agents can securely and easily integrate with external systems, fulfilling the marketing promise that AMCP “integrates with external tools and cloud services” for extended agent capabilities  . In practice, v1.4 has out-of-the-box connectors for a few common services (e.g., a search engine agent connector, perhaps contributed by early adopters), and more will be added via the open-source community.
Interoperability & A2A Compatibility: Even though AMCP is fundamentally asynchronous, v1.4 recognizes the need to interoperate with Google’s A2A and similar protocols. The formal spec doesn’t specifically name A2A, but the marketing analysis notes that A2A is synchronous RPC-focused . V1.4 addresses this by adopting A2A’s message schema as one option for event payloads and by allowing direct request-response semantics on top of the event bus. For example, v1.4 agents can send a direct command event to another agent’s control topic and receive a reply event – effectively mirroring an RPC call but non-blocking . The system uses correlation IDs (conforming to CloudEvents standards) to match replies with requests  . To external systems or developers used to A2A, AMCP v1.4 can appear as a superset: it can do everything A2A does (two agents calling each other) and more (multi-agent pub/sub). This focus on interoperability means organizations can integrate existing A2A-based agents within an AMCP mesh easily. It also lays groundwork for future bridging (e.g., an AMCP gateway that listens for A2A HTTP calls and injects them as events, which is feasible thanks to v1.4’s alignment with A2A schemas).
Multi-Broker & Deployment Support: Per the spec’s design, AMCP decouples the protocol from the transport/broker . V1.4 realizes this with a pluggable EventBroker interface supporting in-memory, Apache Kafka, NATS, and Solace PubSub+ backends . The v1.4 GitHub project includes connectors for these brokers, so users can deploy AMCP in diverse environments: e.g., a dev can start an in-memory broker for testing, while an enterprise can plug in a Solace or Kafka cluster for production. The technical spec in v1.0 described mappings for these brokers, and v1.4’s code confirms support (configuration flags like AMCP_EVENT_BROKER_TYPE=kafka or nats are present  ). Consequently, AMCP v1.4 can leverage enterprise-grade features of those brokers (persistent queues in Kafka for at-least-once delivery, wildcards in NATS for flexible subscriptions, etc.). This is in line with the goal of being cloud-agnostic and transport-agnostic .
Security & Multitenancy: The current version implements a multi-layer security model as outlined in the spec . Each AgentContext authenticates to the broker (using SASL, TLS certs, or NATS NKey depending on broker) ensuring only authorized nodes join the mesh. Within a context, v1.4 has a SecurityManager hook that can enforce topic-level ACLs and role-based permissions on agent actions (e.g., an agent might be prevented from subscribing to certain sensitive topics if not authorized). This addresses the design in the spec where security was critical for multi-tenant cases. The marketing plan stressed that enterprise users demand robust security (mentioning features like encryption, RBAC, and data governance)  . V1.4 provides encryption in transit via TLS (especially when using brokers like Kafka/NATS with TLS and/or deploying in Istio service mesh with mTLS ), and it supports end-to-end encryption of event payloads if needed (the protocol allows payloads to be opaque bytes, so agents could pre-encrypt content). For multitenancy, contexts can be logically separated by authentication realm, and the SecurityManager can isolate agent groups. Some of these features (like a fine-grained policy engine or integration with corporate IAM) are rudimentary in v1.4, foreshadowing enhancements in upcoming versions. But the foundation is there: authentication of contexts, authorization checks on agent operations, and the inclusion of correlation IDs and audit logs for traceability  all align with the initial spec’s security & auditing requirements.
Observability & Management: Recognizing enterprise needs, v1.4 begins to include observability hooks. The Kubernetes deployment manifests in v1.4 show integrated Prometheus scraping on agent pods and brokers  , capturing metrics like active agents, event throughput, etc., and shipping logs via Fluentd . Tracing is also enabled (the Istio integration means distributed traces can be collected for inter-service calls , and correlation IDs in events provide trace continuity across async hops). These features are relatively new in v1.4 and mark a shift from pure functionality to operational maturity. A rudimentary web management interface isn’t fully present yet, but a CLI or simple REST endpoints exist for health and agent listing (the /health and /ready endpoints in AgentContext and the shutdown hook in K8s manifest  show basic control). The formal spec emphasized that AMCP should be deployable and observable in Kubernetes  , and indeed v1.4 has a reference Helm deployment and Istio config for secure intra-mesh comms. Future versions will build on this foundation to improve manageability (as we’ll see in the roadmap).
Alignment with Specification and Strategy: Overall, AMCP v1.4 is a faithful implementation of the v1 spec’s vision – it provides asynchronous event-based messaging, dynamic agent management, and secure multi-agent operation  . It also begins addressing the “critical enhancements” identified in earlier minor versions (v1.1–v1.3), such as stateful migration, lifecycle callbacks consistency, auth context for tools, standardized event metadata, and easier tool connectors . From a strategic perspective, v1.4 delivers the core open-source value propositions needed to attract developers: it’s open (MIT licensed, as noted), interoperable (works with existing agent frameworks by handling comms), and scalable (tested with brokers that handle high throughput). However, many enterprise-oriented features are in early form in v1.4. For instance, the concept of a “guardian agent” for policy enforcement is mentioned in marketing but not fully implemented yet (security is there, but not a packaged policy agent)  . Likewise, seamless integration with frameworks like LangChain or vendor-specific AI services is still largely up to the user (v1.4 provides the hooks, but not yet official adapters for these). The marketing plan’s vision of a complete ecosystem (including SaaS platform, management console, etc.) is not yet realized in v1.4 – which is expected, as v1.4 is the current open-core foundation. In short, v1.4 establishes the technical bedrock: robust protocol behavior (validated by formal reasoning in the spec and a comprehensive test suite spanning Rust, Java, and Python examples), and a flexible deployment model. It sets the stage for the roadmap that will incrementally add the higher-level features, polish, and integrations needed for AMCP to reach its full potential as described in the marketing launch plan.
Example Use Case at v1.4: To illustrate v1.4’s capabilities, consider a “Smart Factory” scenario: multiple MachineAgents publish sensor readings, and a centralized AnalyzerAgent monitors them. In AMCP v1.4, these agents communicate via topics (e.g., machine.press1.status). When an anomaly event is published, the AnalyzerAgent can migrate closer to that machine’s context using dispatchAgent – leveraging v1.4’s strong mobility – to perform detailed analysis on-site. It then uses callMCPTool to query an external maintenance scheduling service, passing along an auth token via the new AuthenticationContext so the API call is authorized. Finally, it publishes a maintenance.alert event that multiple agents (maintenance bots, supervisor dashboard agent) subscribed to. This whole flow (multi-agent pub/sub, runtime migration, secure tool use, multi-receiver notification) is executed reliably in v1.4. The test suite includes similar patterns – e.g., a unit test migrates a CounterAgent across two contexts and verifies its counter state and subscription continue working, and integration tests simulate a ping-pong between agents in different languages and contexts to confirm interop and ordering. These give confidence that v1.4 meets its design goals and can handle real multi-agent workflows.
Having assessed v1.4, we now turn to the future. The following roadmap (v1.5 through v2.4) will guide AMCP from this solid foundation to a feature-complete platform fully aligned with the marketing vision of open-source ubiquity, cloud service, and enterprise adoption. Each version builds on the last, introducing targeted improvements and ensuring backward compatibility (minor releases) or planned transitions (the major 2.0 release) as appropriate. We detail the progression in terms of technical changes and practical impacts, with examples to demonstrate each step.


Version 1.5 – Developer Experience & Multilingual Support
Planned Enhancements (v1.5): The focus of AMCP v1.5 is developer experience and ecosystem integration. This release will make it easier for developers to adopt and use AMCP in their preferred environments, addressing early feedback and paving the way for broader open-source contribution. Key improvements include:
Official SDKs for Multiple Languages: While the core v1.4 implementation is in Java (with a JVM-based AgentContext and agents), the AMCP spec is language-neutral and the v1.0 doc even provided pseudocode/tests in Rust and Python. In v1.5, the project will introduce first-class SDKs for at least Python and Rust, and possibly C#/.NET, to cater to a wider developer base. These SDKs will wrap the AMCP protocol (using the same message schema and broker integration) so that agents can be written in those languages and interoperate with Java agents. For example, a Python developer will be able to pip install amcp-agent and quickly spin up an AgentContext in Python that connects to the same mesh as Java contexts. Under the hood, this might use gRPC or WebSocket to interface with brokers (or even embed a lightweight broker client). Test coverage will verify cross-language interaction – e.g., a Rust agent sends events a Python agent receives, and vice versa, confirming consistent serialization and topic handling. This addresses a strategic need: easing adoption by various developer communities (the marketing plan stresses reaching developers on their terms, and multi-language SDKs are crucial for that broad open-source uptake) .
LangChain & Semantic Kernel Integration Libraries: To make AMCP “plug-and-play” with popular AI frameworks, v1.5 will include integration libraries (or examples) for LangChain (Python) and Semantic Kernel (C#). Concretely, we will provide a LangChain AgentExecutor subclass that uses AMCP under the hood for tool execution or inter-agent communication. For instance, a LangChain agent can offload a subtask by publishing an event to AMCP rather than calling a tool synchronously – our integration will handle that seamlessly. Similarly, a Semantic Kernel skill can be wrapped to send/receive AMCP messages. These integrations fulfill the marketing promise of turning would-be competitors into complements: developers using LangChain/SK can now leverage AMCP as the messaging backbone without abandoning those frameworks  . We’ll include example workflows: e.g., a LangChain QA Agent that publishes a question to AMCP, which a specialized KnowledgeAgent (maybe written in Java) answers, and the response comes back as if it were a LangChain tool result. Tests will ensure that the latency and formatting are handled properly (we might simulate a few multi-agent chains using these libraries to verify everything from prompt formatting to final answer collation). By providing these adapters, v1.5 positions AMCP as an enhancer for existing AI agent ecosystems, easing transition and integration – an important step for developer acceptance.
Developer Utilities and CLI: V1.5 will introduce a simple CLI tool (amcpctl) for common tasks and a developer Dashboard (initial version). The CLI can do things like: create a new agent project (scaffolding the boilerplate in one of the supported languages), run a local broker and context for quick testing (amcpctl dev-start spinning up an in-memory mesh), list active agents and their subscriptions (amcpctl agents ls hitting the context’s management API). This addresses ease-of-use: new users can get an “AMCP agent mesh” running locally in one command, which is great for workshops and hackathons. Additionally, a lightweight web dashboard will be bundled (maybe as part of the AgentContext or a separate container) to visualize agents and messages in real-time. In v1.5 this might be rudimentary (e.g., showing a list of agent IDs, their state, and a log of recent events with topics and IDs ), but it sets the stage for a full management console later. These tools will be heavily tested for developer workflows – e.g., our CI will include a test that the CLI scaffolded project can be compiled and run without errors, and integration tests will spin up two contexts via CLI and ensure they auto-connect and exchange a test event (validating the “dev-start” experience works). Improving the out-of-the-box experience in these ways will lower the barrier for the open-source community and aligns with our marketing push to make AMCP adoption “low friction” for developers .
Improved Documentation & Examples: Alongside the code, v1.5 will deliver extensive documentation: a refreshed spec document v1.5 (updating the formal definitions where needed), how-to guides, and more example use cases. For instance, we’ll include an end-to-end example of a Travel Planner system – expanding on earlier demos – with code for FlightAgent, HotelAgent, etc., showing how they communicate via AMCP. This example will act as both documentation and a test scenario (the build will run it to ensure it produces the expected output, e.g., a combined itinerary). Documentation will also cover best practices (e.g., how to design topic hierarchies for your domain, how to handle versioning of event schemas as your agents evolve). Given that v1.4 was the initial public release, v1.5 documentation improvements respond to community feedback on clarity and will likely incorporate FAQs from early GitHub discussions. We will cite parts of the formal spec in simpler terms for developers. The marketing study highlighted the importance of community and education (talk of webinars, hackathons, etc.)   – v1.5’s docs and examples support that by making AMCP easier to learn and evangelize.
Minor Protocol Tweaks: A few minor protocol/interface updates are planned, driven by developer feedback from v1.4:
Simplified Agent API: Perhaps adding convenience methods like Agent.publish(topic, payload) (so the agent doesn’t always call context.publish(msg)) or a more Pythonic asynchronous iterator for events. These don’t change the underlying protocol but make agent code cleaner.
Extended Metadata: Possibly include a default senderAgent field in events at the protocol level (v1.4 already tags events with sender in practice , but we might formalize it as always present to simplify subscriber logic). This was already informally there, but making it explicit and documented in v1.5 ensures developers can rely on it.
Error Handling Patterns: Define a standard way for agents to signal errors (perhaps a convention like publishing to agent.<id>.error or using an error flag in the message metadata). We will update the spec and implement support so that if an agent throws an exception not caught, the context can publish an error event on its behalf. Test cases will inject faults in agent handlers to ensure the error events are emitted and do not crash the whole context.
These changes will be backward compatible (existing v1.4 agents simply gain new conveniences in v1.5). We will verify that a v1.4 agent library can still communicate through a v1.5 context without issues – the wire protocol remains the same JSON-based event structure (possibly with one or two new optional fields).
Security & Compliance (v1.5): With many new integrations, we’ll also introduce basic governance controls to keep systems secure:
The SecurityManager will get a simpler configuration format (maybe a YAML policy file) so developers can easily set something like “AgentType PlannerAgent can publish only to topics starting with plan.”. This makes it easier to use in dev/test and encourages thinking about security early. It will be documented and an example policy provided (e.g., in the travel example, ensure PaymentAgent can only subscribe to payment. topics, etc.). We will add unit tests for the SecurityManager to ensure policies are correctly enforced (e.g., try a forbidden subscribe and expect a SecurityException).
The authentication for multi-language SDK agents will be designed carefully: e.g., a Python agent connecting to a Java context might use a secure token. We’ll ensure the same authentication model extends to them – likely leveraging the broker’s auth. So if a developer runs a Python AgentContext in one process and a Java AgentContext in another, they’ll authenticate to each other either via the broker or a mutual TLS if direct. This will be documented as well. Essentially, we maintain v1.4’s zero-trust stance (no unauthenticated access to the mesh) even as we simplify usage.
Integration & Interop (v1.5): Besides LangChain/SK integration:
We plan a Kafka Connector enhancement: currently, each AMCP context using Kafka may subscribe to many topics, which can cause rebalancing overhead. v1.5 might introduce an AMCP Kafka Topic Convention (and possibly a Kafka Streams app) to optimize routing. For example, we may consolidate control topics into one Kafka topic with agentId as a key. This isn’t a breaking change but an under-the-hood improvement. We’ll test with a scenario of 100+ agents on Kafka to measure that v1.5 reduces consumer rebalances (ensuring more stable throughput). This aligns with making AMCP more cloud-scalable for the upcoming SaaS service.
CloudEvents Compliance: We already carry correlation IDs and timestamps, but v1.5 will officially mark AMCP event format as CloudEvents 1.0 compatible. This means an AMCP event can be viewed as a CloudEvent (with id, source, type, etc. filled)  . We’ll add conformance tests (e.g., output an event as JSON and validate it against the CloudEvents schema). This fulfills an implicit requirement for interoperability – e.g., enabling integration with Azure Event Grid or other systems that ingest CloudEvents. It’s also a step toward standardization, signaling that AMCP isn’t reinventing the wheel for event format but building on an open standard.
Deployment & Observability (v1.5):
On the Kubernetes side, we’ll refine the Helm charts from v1.4. For example, we might introduce Helm options for enabling the new dashboard or choosing which language runtimes to deploy for agent contexts. We’ll also incorporate Helm test hooks that, after deployment, run a sample agent exchange to verify everything works (essentially an integration test in the deployment pipeline).
Logging improvements: All AMCP components will standardize their log format (likely structured JSON with fields for context, agent, eventId) to ease parsing. We may integrate directly with the Fluentd/Elastic stack by providing a Kibana dashboard for AMCP logs. For instance, if an error event is published, it should appear highlighted in the logs with the agent ID and correlationId, so devs can trace issues. In v1.5, this might come as a default Kibana index pattern and example queries delivered with the monitoring config.
Metrics: We’ll add more metrics counters, e.g., count of events per topic, processing latency per agent, migration count, etc. If possible, use OpenTelemetry metrics so they can be exported to any backend. A new integration test will deploy Prometheus and ensure it can scrape a test metric from an agent (simulate a scenario where an agent records a custom metric via AMCP’s API and Prom captures it).
SaaS readiness (initial): While the full AMCP Cloud is not live yet, v1.5 will start including multi-tenancy hooks in the code. For example, contexts will have a concept of a “Tenant ID” (perhaps derived from credentials) to segregate events if running a shared broker for multiple tenants. This will not be heavily used in open-source deployment, but it’s crucial for our SaaS. We’ll keep it dormant or optional (so self-hosted users aren’t affected), but unit tests will cover scenario: if two contexts have different tenant IDs, ensure they cannot subscribe to each other’s events on a multi-tenant broker (enforced by tenant-scoping in topics or similar).
Testing (v1.5): In addition to the extended integration tests mentioned, v1.5 will maintain the rigorous approach from v1.4:
Formal Proof Update: The formal spec will be updated to reflect any new guarantees (like the refined error-handling semantics). We might include a brief proof that the introduction of guardian policies doesn’t violate safety (e.g., prove that if a policy blocks an event, the system remains consistent).
Unit Tests: Every new SDK will come with its own suite (e.g., Python unit tests using pytest to simulate a couple of events, Rust tests using cargo test similar to the pseudocode in the spec). We aim for parity: the same logical test (ping-pong message, migration scenario, unauthorized action) will be implemented in each language’s test suite to ensure all SDKs behave consistently.
Interoperability Test: A special multi-language test scenario will run: spin up three agents – one Java, one Python, one Rust – have them all subscribe to a topic “test.multi” and have one publish to it. Verify each one got the message and that the payload decoded correctly in each environment. Also test a round-robin chain: Java -> Python -> Rust -> back to Java to ensure messages survive multiple hops and transformations. This ensures the cross-language support in v1.5 is rock solid.
Performance Regression: We’ll also begin tracking performance metrics (throughput, latency) under a standard load test to catch any regressions introduced by the new abstractions. For example, ensure the convenience APIs or multi-language wrappers add negligible overhead. A baseline from v1.4 will be compared to v1.5 runs (perhaps using a simple 1000 events through 10 agents scenario measured in CI).
Use Case Example (v1.5): “Cross-Language DevOps Assistant” – Suppose a company wants to build an AI Ops assistant where a Python monitoring agent detects an incident, a C# diagnostic agent analyzes logs, and a Java remediation agent applies a fix. In AMCP v1.4, they might have needed to write all in one language or handle comms manually. In v1.5, they can use each language’s AMCP SDK: the Python agent (maybe using Semantic Kernel for anomaly detection) publishes an incident.alert event, which the C# agent (running Semantic Kernel with our SK-AMCP integration) picks up. The C# agent then publishes a incident.rootcause event with findings, which the Java agent receives and triggers a fix script. All these message exchanges are seamless across languages. Developer effort to connect these is minimal – they used our provided adaptors and followed documented patterns. This demonstrates how v1.5 dramatically improves heterogeneous agent mesh scenarios. It also proves integration with standard frameworks: the Python agent could have been using LangChain to decide if it should escalate the alert; our integration would allow it to delegate that decision to another agent via AMCP if needed. Essentially, v1.5 makes multi-agent systems more accessible and shows early on that AMCP is not tied to one tech stack, embodying the marketing message of being open and integration-friendly  .


Version 1.6 – Observability & Management Enhancements
Planned Enhancements (v1.6): With the developer experience significantly improved in v1.5, AMCP v1.6 shifts focus to observability, manageability, and cloud readiness. As more users deploy AMCP in complex environments, this version strengthens monitoring, debugging, and begins rolling out management features that will be critical for the AMCP Cloud service and large-scale on-prem deployments.
Advanced Monitoring Dashboard: Building on the basic web UI introduced earlier, v1.6 will debut a more polished AMCP Monitoring Dashboard (likely web-based). This dashboard will provide real-time insights into the agent mesh: active agents (with status and last active timestamp), event throughput per topic, latency heatmaps, error rates, etc. We will incorporate the Prometheus metrics and traces into this UI. For example, one panel might display “Events per second by topic” (sourced from Prometheus queries like rate(amcp_events_published_total[1m]) for each topic), another might list the top 5 agents by CPU or memory (pulling from Kubernetes metrics via the Metrics API or a node exporter). We will also integrate distributed tracing visuals – e.g., if an event X goes through three agents (as indicated by correlation IDs and trace context), the dashboard can show a mini timeline of that flow. This directly addresses the need for traceability highlighted in the spec and marketing (correlation IDs, as ensured by v1.4, now get leveraged into a UI for trace analysis ). The dashboard will be tested with simulated load: e.g., spin up 50 agents, generate events, and ensure the dashboard populates without performance issues. Also, we will verify consistency by cross-checking the dashboard’s data against raw logs/metrics to ensure accuracy.
Management API & Console (Beta): V1.6 will introduce a Management API (likely REST or gRPC) for administrative control of the agent mesh. This includes endpoints to:
Query agent status – e.g., GET /agents returns all agents with their context, state (active/inactive), and subscriptions.
Command agents – e.g., POST /agents/{id}/migrate with target context to trigger a migration (this wraps the internal dispatch mechanism but exposes it via API for external orchestration systems to use).
Update policies – e.g., PUT /policies to live-update the SecurityManager rules (allowing dynamic changes without restarting contexts).
Inject events – e.g., POST /topics/{topic} to publish a test event (useful for manual trigger or integrations).
This Management API will secure itself (likely requiring an admin token or running on a separate secure port). On top of this API, an AMCP Management Console (web UI) can be built. In v1.6, we likely roll it into the Monitoring Dashboard as an “Admin” section – e.g., allowing an admin to select an agent and click “Migrate to Node B” or “Pause” (which would call onDeactivate and stop its event consumption). We will implement a basic pause/resume mechanism: a paused agent in context will not receive new events until resumed – valuable for performing maintenance or debugging. Under the hood, this may mark the agent’s subscriptions as temporarily disabled in the context. We’ll test this by pausing an agent and sending events to its topic – confirming it doesn’t get them during pause, then gets them once resumed (perhaps via a backlog or immediate catch-up if persistent events). These management features realize part of the enterprise ask for operational control over agents (the marketing plan talks about a management console for enterprise users)
. They also set up the backend needed for the SaaS control plane (our cloud service will use the Management API to manage customer agents). We’ll ensure these APIs are thoroughly tested (unit tests for each endpoint’s logic, integration tests using an HTTP client to invoke them in a running context and verifying expected changes in system state).
Enhanced Logging & Auditing: V1.6 will strengthen the logging and audit capabilities:
All significant agent actions (creation, migration, destruction, policy violation) will emit structured audit events. For example, when an agent migrates, the system will log an audit entry like: {event: "AgentMigrated", agent: ID, from: ctxA, to: ctxB, timestamp, traceId}. If using Solace or Kafka with durable storage, we might even publish these to a dedicated agents.audit topic for persistent record (which an “AuditAgent” or external SIEM can subscribe to).
The guardian/PolicyAgent concept begins to manifest here: though full Guardian Agent functionality is planned for a later version, v1.6 might include a simple built-in policy enforcement that logs whenever it blocks an event (e.g., “PolicyBlock: agent X attempted SUBSCRIBE forbidden.topic”) . This not only goes to logs but could also raise an event on an agents.alerts channel, which security monitoring tools could catch.
These additions ensure compliance requirements can start to be met. We’ll test auditing by triggering events that should produce audit logs and verifying those logs are formatted correctly and contain all needed info (we might create a dummy “AuditCollectorAgent” in tests that subscribes to agents.audit and asserts it receives entries for each significant action during the test).
SaaS Multi-Tenancy Features: With an eye on the upcoming SaaS launch (the marketing plan’s AMCP Cloud), v1.6 will finalize core multi-tenancy. This includes:
Tenant Isolation in Brokers: If multiple tenants (customers) share the event mesh in the cloud service, we enforce that an agent from tenant A cannot see events from tenant B. In v1.5 we introduced tenant ID tags; in v1.6, we might integrate this at the broker-level (e.g., using separate Kafka topics per tenant or using Solace VPNs or NATS JetStream accounts per tenant). The code will automatically prepend or segregate by tenant in all subscriptions/publications when multi-tenant mode is on. Version 1.7 – Enterprise Security & “Guardian” Agents
Planned Enhancements (v1.7): AMCP v1.7 is focused on enterprise-grade security, policy enforcement, and reliability. By this stage, the protocol is maturing in features, and some early enterprise adopters (finance, government) will likely be trialing AMCP. Their feedback drives features such as comprehensive policy management (the “Guardian Agent” capability), stronger compliance tools, and high-availability improvements. We also enhance testing rigor (formal verification of security properties, etc.) to satisfy enterprise risk assessments.
Guardian Agent Framework: Version 1.7 introduces a full-fledged Guardian Agent system as hinted in the marketing plan  . This means:
A dedicated Policy Engine that can execute user-defined rules in real-time on events and actions. We will likely implement a DSL or use an existing rule engine (e.g., Drools or a Python-based rule evaluator). Admins can write policies like “If agent of type TraderAgent attempts more than 5 transactions in 1 minute, throttle it” or “Block any event on topic customer.data if not originating from ComplianceAgent”. The Guardian Agent will subscribe to all events (or tap into the AgentContext pipeline) and enforce these.
The Guardian Agent runs with high priority in each context (or centrally) to minimize latency impact. It can either modify/drop events or trigger compensating actions. We will integrate it with the SecurityManager: effectively, some of SecurityManager’s job (static ACLs) might be taken over or supplemented by the Guardian’s dynamic rules.
We will also allow custom plug-in Guardian Agents. For instance, an enterprise could plug in a Python script that implements a custom oversight algorithm (like scanning message payloads for sensitive data patterns). To support this, the framework will provide hooks for custom code execution in response to events (with caution to not degrade performance or safety – likely executed in a sandbox or separate process to isolate any slowdowns).
Testing the Guardian features is critical: we’ll create various rules and ensure they fire appropriately. For example, simulate a suspicious event and confirm the Guardian blocked it and emitted an audit log “PolicyBlock” (and perhaps a quarantine event to a security topic). We’ll also test performance: ensure that with an active Guardian, normal throughput doesn’t drop significantly (perhaps by using caching in the policy engine, or letting rules specify which topics they apply to so not every event goes through every rule). Formally, we might model some policy in TLA+ to verify it cannot cause deadlocks or inconsistency (since a policy could theoretically interfere with message ordering; we’ll design it so policy actions are themselves events, to keep everything event-driven and traceable, which aligns with AMCP’s design principles).
Fine-Grained Access Control & Encryption: V1.7 will allow per-topic encryption keys and more granular access control lists:
We might integrate with a KMS (Key Management Service) such that certain topics are configured to encrypt payloads with a customer-managed key. Only agents with the decryption ability (managed by the SecurityManager with appropriate key) can read them. This is aimed at customers like banks that require end-to-end encryption for sensitive data on the mesh, beyond transport-level TLS. Implementation-wise, the agent SDK could handle encryption/decryption if configured (so it’s transparent to app logic). We’ll test that by marking a topic “secure.*” with a key, publishing an event, and verifying only an agent with the key can decode it (others get gibberish or an error).
The SecurityManager/Guardian will now support role-based permissions on specific actions. E.g., define roles like “admin-agent” vs “guest-agent” and allow only admin-agents to create new agents or to subscribe to confidential topics. In practice, this may have been partly doable with earlier ACLs, but v1.7 formalizes it with a role attribute on Agent (in metadata or certificate) and an authorization check on sensitive operations. We will create test agents with roles and ensure policies enforce correctly (attempt a forbidden action and expect SecurityException or policy block). This caters to multi-team or multi-app meshes where not all agents are equally trusted.
High Availability & Fault Tolerance: Enterprise users will expect not just basic failover but seamless HA:
Redundant Agent Contexts: v1.7 will introduce an option for running agents in a replicated mode for fault tolerance. This could mean two instances of an agent (in different contexts or AZs) operating in parallel, with only one active at a time but hot standby. AMCP can use broker features or a leader election to coordinate which instance is active (similar to how Kubernetes leader election works). This is particularly useful for stateful agents that must be highly available (e.g., an OrderProcessingAgent). We might implement a feature where if an agent is marked highAvailability:true, the system automatically keeps a clone in standby and if the primary dies or becomes unreachable, the clone takes over (using a combination of heartbeat messages and broker acknowledgement to detect failure). This will be complex, so it might be experimental in v1.7. Testing will involve killing an agent context process and verifying the standby agent picks up within X seconds and no events are lost (by using persistent broker storage and the standby having the same subscriptions, which now become active). This effectively builds on the migration mechanism but in an automated way. We’ll likely lean on known patterns (like if using Kafka, have both instances consume but one as “idle” via consumer group coordination).
Ordered Delivery Guarantees: For certain workflows, strict ordering across multiple topics might be required. While AMCP always preserved per-topic order , v1.7 might offer sequence alignment: e.g., ensure that events marked with a sequence number (especially across partitions in Kafka or across contexts) are delivered in order or trigger an out-of-order alert. We will add a mechanism (perhaps via the Guardian agent or a special subscriber) to detect gaps or reordering in critical sequences. This is a niche feature for, say, financial transactions that need total ordering. We will simulate out-of-order scenarios in tests (manually shuffle events) and see if the system catches it or buffers to restore order when possible.
Enterprise Connectors & Integrations: Expand the suite of connectors:
For example, a Database Connector Agent that can execute SQL queries triggered by events, or an Email/Messaging Connector for notifying humans. While the core of AMCP remains the protocol, providing these connectors (perhaps as part of an enterprise “toolkit”) increases AMCP’s utility out-of-the-box. In v1.7, we could introduce a ServiceNowAgent or SalesforceAgent that listens for certain events and creates CRM entries, as suggested by the marketing plan’s focus on integration with existing systems for value-add. These will come with integration tests hitting mock endpoints (to ensure the connector logic works).
Integration with Identity Management: If not already, by v1.7 we want AMCP to integrate with corporate identity systems. That might mean an agent can query an LDAP/AD to get user roles to decide something, or that the AMCP management console can delegate auth to SAML/SSO. Most of this is around how the Guardian or SecurityManager authenticates agent identities – e.g., an agent might present a JWT signed by enterprise IDP so the SecurityManager knows its role. We will implement and test flows where an agent connects with a token representing a service identity and ensure the system extracts the asserted identity and enforces the appropriate policies for it.
Compliance & Audit Tools: V1.7 will likely coincide with early enterprise reviews (security audits, compliance checks). In response, we might add:
Audit Trail Exporter: a built-in process or agent that can export audit logs to common SIEM systems (Splunk, ELK, etc.) in real-time. Possibly using the standard syslog or CEF format for easy ingestion into security monitoring. In testing, we’ll configure a mini-ELK stack and ensure our exporter can send a test audit event and it appears in Kibana correctly.
Compliance Reports Generation: Perhaps a command or script that reads the audit log events and generates human-readable reports for a period (e.g., “Agent X accessed data Y 3 times on date Z”). This isn’t core protocol but very useful for users – we might provide a template or a small web UI in the console for “export compliance report” which queries the events stored (since we have them in persistent storage via the broker or a dedicated store).
Formal Verification of Security Properties: We could invest in a formal model (e.g., using TLA+ or Alloy) of AMCP’s security features (like proving that an unauthorized agent cannot subscribe to a protected topic under the given model). This is more on the research side, but delivering a brief formal proof appendix with v1.7 documentation could increase confidence for risk-averse clients. We’ll base it on the earlier formal spec logic, extended with security state and transitions. For instance, prove that given a set of policy rules, an agent without proper credentials will never receive an event on topic T (safety property). Having such proofs, even if in an appendix, aligns with marketing to highly regulated customers that AMCP was “designed with formal methods ensuring compliance” (something we can brag about).
Testing & QA (v1.7):
At this stage, our test suite is extensive. We will add targeted stress tests on security and HA. For example, run a constant high-load scenario with Guardian policies enabled and ensure no policy breaches (i.e., test that under load, the Guardian doesn’t erroneously allow something or crash). Also, test recovery scenarios in loops: repeatedly kill and restart nodes in a 5-node mesh while sending events, verifying system stability (perhaps automated with a chaos engineering tool).
Penetration Testing: We will perform internal pen-tests on AMCP, trying actions like message spoofing, replay attacks, unauthorized access, etc. If any vulnerabilities are found, v1.7 will patch them (e.g., ensure message IDs are cryptographically random to prevent guessing, ensure old revoked tokens are not accepted, etc.). We might bring in third-party security auditors as well to certify the design.
Ensuring that the introduction of Guardian and other features doesn’t introduce significant latency: measure end-to-end latency with and without Guardian under small load and heavy load. If overhead is high, optimize policy rule evaluation (maybe compile rules to code or run them in parallel pipelines). We aim to keep additional latency minimal (sub-millisecond on average).
User Acceptance Testing: If we have design partners, by v1.7 we’d likely run pilot projects with them. Feedback from those pilots (ease of writing policies, clarity of logs, etc.) will be incorporated. For instance, if a bank finds the DSL for policies too limited, we might extend it or document workarounds in this release.
Use Case Example (v1.7): “Automated Trading with Risk Guardrails” – A financial firm deploys multiple TraderAgent bots that execute trades based on market signals, and a RiskGuardianAgent that oversees them. With AMCP v1.7:
Each TraderAgent publishes trade.request events when they want to execute a trade. A centralized ExecutionAgent carries them out (placing orders via a market API).
The RiskGuardianAgent (leveraging the new Guardian framework) is set up with policies like: “If any single TraderAgent’s requests exceed \$10M in 1 hour, flag and hold further requests” and “If trade.topic contains a restricted asset, require ComplianceAgent approval”. As trade events flow, the Guardian monitors volumes per agent (maintaining state over time, possibly using the policy engine’s aggregation capability) and can intervene by issuing a trade.hold event targeting the ExecutionAgent if limits are breached.
Meanwhile, all trade events are encrypted with the firm’s KMS key on the topic level. Only the ExecutionAgent and a ComplianceAgent have the key to read full details, others only see anonymized info. This ensures confidentiality (even if the broker or an outsider got the data stream, it’s gibberish) – an audit requirement.
The system runs in an HA configuration: each TraderAgent is actually deployed in two pods for redundancy. AMCP’s HA mechanism ensures that if one pod goes down mid-day, the standby seamlessly takes over processing that Trader’s events (perhaps by having a mirrored subscription that activates without message loss). The trading continues unaffected, meeting the firm’s 24/7 reliability needs.
At end of day, the firm’s compliance team uses the new audit tools to generate a report of all trades and any policy flags. The GuardianAgent logged one incident of a TraderAgent hitting a limit, which it blocked – the report shows “Agent123 attempted trades totaling $12M, exceeding limit. Guardian blocked 2 trades at 14:35 UTC .” This gives the compliance officers clear visibility and they can further investigate by replaying those events if needed (since AMCP retained them in the audit topic).
In this scenario, v1.7’s features shine: the Guardian Agent prevented rule violations in real-time, fulfilling the “autonomous oversight” that was anticipated by Gartner and promised in our marketing as a differentiator . The fine-grained security (topic encryption, role restrictions) ensured that even in a sensitive financial environment, the agent mesh protected data and adhered to company policy. The trading system benefitted from AMCP’s HA and scaling – the firm can run many trader bots in parallel, knowing the protocol can handle the load and recover from failures. This builds trust that AMCP is enterprise-ready for mission-critical operations, validating the strategic investment in these capabilities.


Version 1.8 – Scalability & Performance Optimization
Planned Enhancements (v1.8): As AMCP’s feature set grows, version 1.8 turns towards scalability, performance tuning, and cloud-native optimization. This release is about making sure AMCP can handle massive agent networks with high throughput, as well as refining the developer and ops experience on the margins. It also integrates feedback from any beta SaaS deployment at scale.
Scalable Broker Fabric & Mesh Federation: Thus far, AMCP has relied on existing brokers (Kafka/Solace/NATS) for distribution within a mesh. In v1.8, we explore federating multiple broker clusters to scale beyond a single cluster’s capacity or to span multiple regions with low latency:
Introduce the concept of Region or Zone in AMCP. For instance, agents might be tagged with a region (like us-west vs eu-central) and the system can route events regionally when possible, or use a Bridge Agent to relay across regions. We might leverage Kafka MirrorMaker or Solace DMR underneath but expose it as an AMCP configuration (“connect meshes”). The effect is an AMCP federation where an event can automatically propagate to other federated meshes if needed, but local traffic stays local (reducing bandwidth).
This addresses scenarios where a company has agents deployed in different cloud regions or on-premises locations and wants them to communicate (the marketing plan envisioned a global event mesh for the SaaS offering ). It also improves scalability by partitioning agent sets. We’ll test federation by deploying two separate Kafka clusters and configuring AMCP to treat them as one federated mesh, then sending events from an agent on cluster A intended for an agent on cluster B, verifying they arrive via the federation link with acceptable latency and throughput.
Dynamic Load Balancing: To further scalability, v1.8 may introduce an Agent Load Balancer concept. If one context is overloaded with too many agents or events, the system (perhaps via the Orchestrator or a new system agent) can redistribute agents dynamically. We have migration and HA pieces from earlier versions; here we add automation: monitoring agent CPU/memory usage (we have those metrics from earlier versions) and automatically migrating or cloning agents to spread load across contexts/pods. We’ll develop a strategy such as: if an AgentContext’s event loop lag or CPU exceeds threshold, trigger migration of some agents to less busy contexts. We will simulate uneven load in tests (one context handling 100 agents, another 5) and see if the balancer moves some to even it out, verifying performance improvements and no disruption of service (other than planned brief migrations).
Throughput Optimization: On the broker integration side, we’ll refine settings (like Kafka producer batch sizes, NATS JetStream windowing, etc.) specifically for AMCP patterns. We might include a fine-tuned NATS JetStream mode for AMCP that uses subject wildcards efficiently for broadcasting to many agents with lower overhead than naive subscriptions (maybe by grouping subscriptions per process). Another angle: if an agent is subscribed to a very high-volume topic but processing slowly, we could implement backpressure – contexts could detect slow consumer and either drop messages (if marked fire-and-forget) or signal producers to slow down (some brokers support advisory backpressure). These are advanced and broker-specific, but v1.8 will document recommended configurations or even adjust defaults to optimize throughput and latency based on our internal benchmark results. We will re-run large-scale benchmarks (with tens of thousands of events per second, or thousands of agents, if resources allow) and aim to see linear scaling and minimal bottlenecks. Metrics from these runs (like 99th percentile latency) will guide adjustments.
Lite Agent Runtime & Edge Optimization: To support IoT and edge scenarios (as hinted by interest from manufacturing/logistics sectors), v1.8 will introduce an AMCP Edge Runtime – a slim, possibly C/C++ or Rust based agent container that can run on resource-constrained devices (Raspberry Pi, industrial controllers). This might not support the full feature set (maybe no heavy Guardian logic on the edge), but it will allow basic pub/sub and stateful logic. We’ll test deploying this on a small Linux board and ensure it can join the mesh (perhaps via MQTT or NATS which are IoT-friendly). The goal is to reduce memory footprint significantly (targeting under 50MB RAM and low CPU). This expands AMCP’s applicability in environments like factories or vehicles, which was part of the vision (multi-agent systems in IoT).
One-Click Cloud Deployment Tools: Although primarily relevant for our SaaS, we also want to simplify on-prem/hybrid deployment further. V1.8 may come with a Terraform module or CloudFormation template that sets up AMCP clusters on popular clouds (AWS, Azure). For example, a Terraform script to provision a Kubernetes cluster, deploy Zookeeper+Kafka and AMCP pods, with appropriate networking and autoscaling. This goes hand-in-hand with scalability: making it easy for users to scale up their infrastructure. We will test these templates by actually deploying a full environment on each target cloud and running the basic test suite to confirm it works. Essentially, we move toward an “appliance” feel for enterprise customers who want to self-host – maybe even a “AMCP Operator” for Kubernetes that manages the AMCP deployment CRDs (this could be considered, though might slip to a later version).
System Hardening & Fine Tuning: By v1.8, we gather a lot of real-world usage data. We will do another round of profiling and optimization at the code level:
Streamline hot code paths in AgentContext (like event dispatch loops, lock contention – perhaps moving to a lock-free queue if necessary, or using a thread pool more efficiently).
Memory leaks or build-up will be tackled – use of heavy caches by Guardian or persistent state by agents will be reviewed under longevity tests (run a mesh for a week continuously and see memory). We’ll incorporate any fixes needed for long-running stability.
Possibly upgrade underlying libraries (maybe a newer Kafka client with better throughput, etc.) and test compatibility.
Also, refine the testing tools – by now we might have an official performance test harness. We could open source that to the community in v1.8 so others can benchmark their setups.
Developer & Quality of Life Improvements: While focus is performance, we won’t neglect developer QOL:
Provide Hot Reload of agent code in development mode. E.g., a Java agent can be reloaded without restarting the context (like jrebel, or by running the agent in a child ClassLoader that can be swapped). For Python, maybe easier since it’s dynamic. This greatly speeds up the code-test cycle for agent developers. We’ll mark it as dev-only (not for production use). Test by modifying an agent’s behavior in a running system and confirming it starts doing the new behavior without losing state (where feasible).
Agent Versioning Support: By v1.8, multiple teams might be deploying updates to their agents on a running mesh. We add a notion of agent version and perhaps allow side-by-side version deployment. For example, an AgentContext might host both v1 and v2 of an agent during a rolling upgrade, and route a percentage of traffic to the new one (like canary). This could be implemented by topic partitioning (e.g., new agents listen on topic.v2 or have a filter metadata). We’ll formalize a strategy for incremental upgrades with minimal downtime. In testing, we’ll simulate deploying a new agent version and ensure the old and new can co-exist and that we can switch fully to new and retire old gracefully via the management API (maybe a “drain” command that migrates all tasks off an older agent instance then stops it).
Improvements in the CLI and Dashboard based on user feedback: maybe add search functionality in the dashboard (find an agent by name), or health indicators (e.g., highlight if an agent has not received any messages for a long time when it normally should – indicating a potential problem upstream). Minor features like these, driven by user stories, will be sprinkled in.

Version 2.0 – Major Release: Modularization and Enterprise Platform
Planned Breakthroughs (v2.0): AMCP 2.0 marks a major evolution – it is the culmination of the 1.x developments and likely introduces architectural enhancements, modular packaging, and official enterprise platform release. The aim is to incorporate lessons learned to ensure AMCP can serve as a stable foundation for years to come, while possibly breaking compatibility to clean up technical debt or incorporate major new technology. We align this release with launching AMCP as a fully productized platform (open-source core 2.0 and the commercial offerings around it).
Modular Architecture & Packaging: In 2.0, the AMCP core might be restructured into distinct modules:
AMCP Core Protocol Library: a slim library containing the fundamental event routing, AgentContext, and interface definitions. This library would be the one standardized piece, which can be implemented in multiple languages. By 2.0, we might even rewrite parts in Rust for performance and then have bindings to Java/Python (if not already done). The idea is to clearly separate the protocol engine from plugins.
AMCP Services (Optional Modules): things like the Guardian agent, connectors, etc., become plug-and-play modules. For example, an organization that doesn’t need mobility could run a lighter stack without the MigrationManager loaded (to reduce overhead). Or a minimal IoT deployment might exclude the entire Guardian/security module if running in a closed network. 2.0’s architecture will support this modularity, possibly through a microkernel approach where the AgentContext loads only the needed components at startup based on config. This addresses any bloat that accumulated – making AMCP leaner and more flexible.
2.0 Packaging: We will provide distributions for different needs: e.g., AMCP Edge (very lightweight, no guardian, limited broker support, ideal for IoT), AMCP Standard (full feature set with default modules), AMCP Enterprise (bundled with all connectors and guardian modules fully enabled, maybe a hardened config). This aligns with open-core vs enterprise differentiation: the open source core is in all, enterprise edition might just be pre-configured with extras and come with support. Technically, though, they share the same 2.0 codebase to avoid forks.
We will test that customizing the module set doesn’t break things – e.g., run AMCP without the mobility module and ensure agents don’t unexpectedly call migrate (and if they do, a clear error is given). Also measure memory footprint in minimal vs full mode to quantify the benefits of modularization.
Protocol Enhancements: Given 1.x was feature-rich, 2.0 protocol changes might be minimal, but we could introduce some breaking improvements:
Unified Communication Bus: We might decide to implement a native messaging layer for AMCP (instead of always relying on third-party brokers). Perhaps using a modern approach like NATS as the embedded default (or a custom event bus for internal communications, while still allowing external broker integration). If v1.x faced limitations with external brokers, v2.0 could have its own broker optimized for agent messaging patterns (lots of small messages, lots of topics, strong ordering, etc.). This could increase performance and give us end-to-end control (and still interop via gateways for Kafka/Solace if needed). If we go this route, heavy testing is needed to ensure it outperforms or at least matches the reliability of established brokers. Possibly we integrate an existing proven engine (like embedding NATS for default, with an option for external Kafka if desired).
Simplified Syntax: Maybe unify the concept of control events vs normal events. E.g., in 1.x we had agent.<ID>.control topics for agent-specific commands. In 2.0, we might abstract that so that one can call an agent method via a simpler API and under the hood it’s just an event. Or provide first-class support for request-response at protocol level (like an “expect reply” flag to auto-manage correlation). Minor improvement since 1.x already does correlation, but could sugar it.
Another possible enhancement: Time-Triggered Events or scheduling at protocol level (not just by user code). For example, an agent could ask the context “publish event X at time T” – context will handle scheduling. Now in 1.x one can do that with an external scheduler or sleep, but making it a feature might improve clarity (especially for use cases in IoT or automated routines).
We ensure the protocol is fully backward compatible for basic operations: A v1.9 agent might still be able to communicate on the same broker with v2.0 agents (if using older features only). However, if we introduced an internal broker, mixed operation might not be trivial. We will likely provide a gateway or compatibility mode: e.g., run an AMCP 2.0 context in a "1.x compatibility mode" where it connects to Kafka the old way, to allow gradual upgrade of distributed deployments. This backward compatibility mode will be tested by scenario: spin up some v2.0 contexts in compatibility mode with a v1.9 context still running and ensure messages pass correctly (thus customers can do rolling upgrades).
Enterprise Platform & SaaS Integration: Version 2.0 likely coincides with making the AMCP Enterprise Platform fully official. This means:
The AMCP Cloud SaaS is out of beta and all features align. 2.0’s management API is stable and encompassed by the SaaS control plane. We ensure any adjustments needed for multi-tenancy at extreme scale (maybe multi-level tenancy or usage quotas enforcement) are included.
GUI Management Console 2.0: Possibly a more polished web app (maybe even as a standalone service) for controlling AMCP deployments cluster-wide. Could integrate with Kubernetes (like showing pods status, allowing scaling operations from the AMCP console). By now, the line between AMCP and its deployment environment could blur – e.g., hooking AMCP’s agent management with K8s Operators such that deploying a new agent type might spin up a new container via Operator.
We might incorporate a Marketplace/Hub concept: since AMCP is open-core, we could provide a repository (hub) for user-contributed agents, connectors, and policies that can be downloaded and plugged in. The 2.0 console could have a section to browse and install such extensions (with one-click, pulling from our artifact repository). This fosters the ecosystem – e.g., a company wants a SlackConnectorAgent, they find it in the marketplace, click install, and it runs.
Integration with DevOps pipelines: 2.0 will smooth how agents move from dev to prod. Perhaps by providing a direct Jenkins/CI plugin or ArgoCD integration. For example, an agent’s container image once built can register itself with the AMCP mesh (maybe update a config map that triggers the Operator to deploy it). We try to streamline that pipeline. Testing: simulate a CI pipeline pushing a new agent version and ensure our system picks it up for deployment with minimal manual steps (closing the loop from code to running agent).
Security & Governance 2.0: With 2.0, we aim for zero trust at scale:
Possibly implement default Mutual Authentication for agents at the application level: e.g., all events could be signed by the sending agent’s key and verified by receivers. 1.x focused on transport encryption and trust mostly at context level, but 2.0 might push it further down to each agent identity (especially if the context is hosting multi-tenant agents, which we allowed, though typically each context was partly trust boundary). If we go that route, we integrate a PKI for agents. This can be done in a backward-compatible way by including a signature and agent certificate in event metadata (optional for those who need, mandated in high security mode). It would add overhead, so we allow turning it on per topic or per agent. We test that an agent with a valid cert is accepted and a rogue agent with no cert is rejected by others (assuming out-of-band distribution of trust roots).
Enhanced governance: perhaps a central policy store and dashboard where you can manage all Guardian rules across the org, simulate their effect, and audit changes. 2.0’s console might include a “Policy Studio” for writing and testing guardian policies with a sandbox. This would cater to risk officers who want to adjust rules without messing with code.
Achieve certifications – by 2.0 we might attempt to certify AMCP under some security standards (if not earlier). If FIPS compliance or Common Criteria evaluation is necessary for some clients (like government), we ensure our crypto and architecture can get there (which might involve documentation rather than code changes at this point).
Performance & Scale Goals: Even though 1.x scaled well, 2.0 might set new goals, like an order of magnitude beyond: maybe target 100k agents or million messages per second in high-end deployments (taking advantage of more efficient internals or advanced clustering). We would do a massive benchmark on a cloud cluster specifically to demonstrate 2.0’s improvements (which will be a highlight for marketing a 2.0 release).
Deprecations and Breaking Changes: We will remove whatever was deprecated in 1.x. E.g., if older API calls or config formats existed, 2.0 cleans them out. Also, if we reworked internal components, e.g., replaced the underlying broker with our own, then the way you configure external broker might change (like telling 2.0 to run in “external broker mode” vs default internal). We’ll provide migration scripts for config files, and big upgrade notes. For code, since most agent logic was decoupled from the infrastructure, agent code likely doesn’t break, but if any library API changed (say, the AgentContext.createAgent signature changed to accommodate something), we will provide adaptors or at least clear compiler errors to fix. We already prepared users in v1.9 for this.
Testing (v2.0):
Despite being a “new” version, we carry forward the exhaustive tests. We will repeat all essential tests from 1.x under 2.0 (some might require slight adaptation if APIs changed, but the scenarios remain).
If introducing an integrated broker, we’ll test it under failure scenarios and ensure it matches external brokers’ durability (simulate a crash of an AMCP node and see if messages persisted or need re-sending).
Interop tests with v1.x (if we offer compatibility mode or gateway).
Possibly a beta program for 2.0: we might have some friendly users test 2.0 RC in their environment to catch any real-world corner cases we didn’t foresee. Use their feedback to refine before final 2.0 release.
Because 2.0 could be widely adopted as the new base, we’ll incorporate fuzz testing for inputs, and maybe formal verification of any new algorithm (like if we wrote a custom consensus for HA, formally verify no split-brain, etc.).
